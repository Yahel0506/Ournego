## Manifest and dependency changes

Bundletool confirmed these permissions in the inspected artifact:

- `ACCESS_FINE_LOCATION`: map and business location; `INTERNET`: network services; `ACCESS_NETWORK_STATE`: connectivity; `RECORD_AUDIO`: voice search.
- `CALL_PHONE`: contributed by `flutter_phone_direct_caller`. The plugin was removed here as unused, but the business sheet's "Llamar" button depended on it (lost in the floating-sheet refactor), so it is restored. `PhoneCallLauncher` calls directly when granted and falls back to `tel:` when the permission is permanently denied.
- `USE_BIOMETRIC`, `USE_FINGERPRINT`: contributed by AndroidX biometric; `READ_GSERVICES`: contributed by Google reCAPTCHA. These are transitive SDK permissions in the old bundle; removal after dropping Firebase must be confirmed in a new merged manifest. Do not blindly suppress them while their remaining dependency requirements are unverified.
- `com.ournego.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`: generated signature-level permission for AndroidX receivers.

Removed unused direct dependencies `firebase_core`, `firebase_auth`, and `cloud_firestore`. (`flutter_phone_direct_caller` was removed in this audit and restored later; see `CALL_PHONE` above.) Google Services Gradle configuration and `google_sign_in` remain: removing Firebase Dart plugins does not establish that Google configuration is unused. Other unreferenced packages were not removed merely because direct imports are absent: tooling, generated code and transitive uses require separate assessment. Existing Linux/Windows generated registrant changes predate this audit and were preserved.

The AAB was not rebuilt. Therefore its SDKs and permissions remain unchanged; after a release rebuild, inspect the actual bundle and merged manifest again, including the biometric and Google permissions, and smoke-test Google sign-in, location, microphone and photo selection on Android.

## RLS and anon access: repository evidence

Supabase's public key is an identifier, not authorization. [Supabase documents](https://supabase.com/docs/guides/database/postgres/row-level-security) that effective access depends on grants, enabled RLS and all applicable policies; functions, views and Storage need separate review. With a user session the same client key can reach `authenticated` policies. A static review cannot establish deployed schema, migration order, existing permissive policies, grants, exposed views, functions, bucket policies, or actual provider state. **RLS protection of the deployed database is not confirmed.** No SQL was executed.

| Tables or objects | Evidence and gaps in checked-in SQL |
| --- | --- |
| `businesses`, `business_hours`, `business_products`, `business_exceptions` | `2026-11-05_business_review_status.sql` defines public visibility predicates for approved active listings and child rows, plus owner/reviewer rules. It does **not** enable RLS on these pre-existing tables, and assumes prior policies/grants. `2026-11-05_business_review_status_test.sql` exercises anon businesses and hours; product/exception anon coverage is not established by that test. Other lifecycle tests exist. Historical policies can combine permissively. |
| `reviewers`, `business_review_log` | RLS enabled and authenticated self/owner/reviewer read policies defined; review tests exercise access. Effective grants and old policies remain to verify. |
| `account_deletion_requests` | RLS enabled, authenticated own-row read policy, and anon/authenticated privileges restricted; dedicated RLS and request tests exist. |
| `account_deletion_settings`, `account_deletion_dispatches` | RLS enabled, anon/authenticated privileges revoked, and no direct client policies defined in the checked-in migration; this can be intentional default-deny. Deletion tests cover workflow, not a complete table-policy matrix. |
| `user_interactions` | RLS enabled, but `SELECT` uses `true` and `INSERT` uses `true` for both anon and authenticated. Subject to grants, guests can read all rows including `user_id` and metadata, and submit arbitrary permitted rows or attribute them to another user. No dedicated anon RLS test found; deletion tests only cover cleanup. Review privacy, attribution and abuse controls. |
| `users`, `reviews`, `user_favorites`, `feedback`, `feedback_attachments`, `businesses_pictures` | Referenced by client code; no corresponding table policy definitions found in the reviewed SQL directories. Actual RLS/grants and dedicated access tests are unverified. Some similarly named client references are Storage buckets; inspect actual schema separately. |
| `storage.objects` and buckets (`profile_pictures`, `businesses_pictures`, `feedback_attachments`) | No Storage policy definitions found in these directories. Bucket public/private configuration, object ownership and write restrictions are unverified. |

Before release, a project administrator should read the live table inventory, `relrowsecurity`, grants, `pg_policies`, exposed views, security-definer RPC grants and Storage policies; compare with the full migration history, and run role-based read/write regression tests in a suitable isolated environment. Verify both anon and authenticated access, including alternate permissive policies and owner/reviewer boundaries. Review `user_interactions` as a priority. These checks remain pending; avoid treating the checked-in fixtures as proof of production state.

## Provider restrictions and manual release work

- **Mapbox:** manually use a separate mobile public token with only the public scopes needed by the app; never ship secret scopes. Monitor usage and rotate if needed. Use a separate URL-restricted token for web; [Mapbox documents](https://docs.mapbox.com/accounts/guides/tokens/) mobile/URL-restriction limitations. Verify actual request compatibility before applying any restriction.
- **LocationIQ:** manually check the account's currently supported key restrictions and quotas, isolate a mobile key, and monitor usage. Mobile keys are extractable; do not assume a referrer or IP restriction protects an Android client. If available restrictions cannot protect the required API, assess a rate-limited server-side proxy. Verify with LocationIQ's current account documentation before applying changes.
- **Google/Firebase:** in Google Cloud/Firebase, inspect the actual key and enabled APIs; restrict APIs to those needed and, where compatible, restrict Android keys by package and signing-certificate SHA-1. Confirm which OAuth clients and Firebase services use each key, and test sign-in and any remaining services after changes. See [Firebase API key guidance](https://firebase.google.com/docs/projects/api-keys). Never ship service-account JSON or private keys.
- **Play Console:** pending manual creation of a developer account, app setup, Play App Signing and store release. Once Play signing is enabled, obtain the actual app-signing certificate fingerprint and configure compatible Google OAuth/API restrictions alongside the upload/debug fingerprints as appropriate. Verify Google sign-in in a Play-installed build; no Play action has been performed.
- Rebuild only when needed, re-audit the new AAB and manifest, run signing and device checks, and record provider configuration and live RLS verification without recording key values.
